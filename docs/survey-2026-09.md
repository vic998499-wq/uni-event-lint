# 基线率采集：30 个 uni-app 仓（2026-09）

> **问题**：`e.target.value` 这个写法在真实的 uni-app 项目里到底有多常见？
> 值不值得为它做一个工具？

## 取样规则（先定死，顺序全取，不挑）

GitHub 搜索 `topic:uni-app` ∪ `topic:uniapp`，`language:Vue`，
**按 star 降序取前 30**，顺序全收 —— 包括我预期干净的。挑出来的样本没有意义。

- 取数：`codeload.github.com` 的 tar.gz + `gzip -t` 完整性校验
- 扫描：**本仓打包后的 CLI**（`node bin/cli.js DIR --json`），不是实验脚本 ——
  表和它所文档的工具必须是同一件东西
- `.vue < 10` 记为「不适用」，**记录不丢弃**
- 每行带**分母**（有多少 .vue 在处理输入事件）和**解析健康度**

## 采集过程中修掉的仪器缺陷

这一轮**没有一次是"跑一遍就得到数字"**。每一条都是先量出一个看着合理的数，
再发现那个数是假的：

| # | 症状 | 真相 |
|---|---|---|
| 1 | 第一版扫描器报 7 条 | **6 条误报** —— `dataset` / `id` / CSS 选择器字符串。凯米那道门能用是因为背后有**登记表**；公开 linter 不能有 |
| 2 | 某仓报 6 条 | 全在 `vue-element-admin` 的**网页后台**里 —— 那儿 `target.value` 是对的 ⇒ 加 `pages.json` 作用域判定 |
| 3 | 某仓报「.vue 0」却「有输入事件 19」 | 自相矛盾。uni-app 源码在 Spring Boot 的 `resources/**static**/` 下，被我的跳过列表吃掉 **169 个文件** |
| 4 | 两个仓报「.vue 0」 | 现代模板的 `pages.json` 是**自动生成 + gitignore** 的，只认它就会整仓排除 ⇒ 加 `pages.config.*` |
| 5 | `hello-uniapp` 报 0 命中 | 其中 1 个文件**没干净解析** —— `ts.createSourceFile` 语法错**不抛异常**，被解析坏的文件静默返回 0 |
| 6 | 一张 58 行、27 个仓重复的结果表 | 我 `TaskStop` 掉第一次采集**它没死**，又在它底下改了脚本，两个实例共用克隆目录互删。**看着像数据** ⇒ 作废重采 + 单实例锁 |
| 7 | `tar: Cannot connect to C: resolve failed` | GNU tar 把 `C:/x` 当成**远程主机规格** `host:path`。我手动验证时用的是 `/c/x`，所以那次"成功"了 —— **验证面少复现一条真实条件，量出来的每个数都是假的** |

第 3、4、5 条是同一类：**「0 命中」说不清是哪一种 0。**
所以本工具坚持把「扫了几个 / 排除了几个 / 解析干不干净」和结果一起打出来。

## 这个数该怎么读

**能说的**：
- 10~14% 不算低。多数 lint 规则的触发率比这还低。
- **0 误报 / 29 个仓** —— 这是一条 lint 规则能不能活下来的那个数。
- 命中的都在**会被抄走**的代码里：一个 2.8k★ 组件库的演示页、两个商城模板。
  实际影响面比 4/29 大。

**不能说的**：
- 样本偏**热门**仓，而这个 bug 和「项目越个人化越容易犯」正相关
  （样本外另扫到一个个人商城项目，5 条，同款）。真实比率可能更高。
- 29 个里有相当比例是**组件库**（只 emit 不 consume），真实分母可能更小。
- 单次采集，没有重复测量。
